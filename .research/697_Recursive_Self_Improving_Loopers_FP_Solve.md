## TL;DR

Inkling-2-Mini (26.4B MoE, 3.4B active) runs layers 6–17 **3× per token** by default. Forcing 4 passes collapses it (95.3% repeat loops; DeepScaleR 50.0%→3.1%): at Layer 17 ONE hidden direction reverses sign between passes 3→4 (`v1` carries 75.5% of the pass-shift energy, −121.2→+114.6), and the 48 cross-pass memory gates — which never saw a positive `+114.6` input in pretraining — collapse (mean +0.638→+0.067). The repo's **FP-Solve** repairs this in 5.8 minutes with **zero backprop, zero labels, zero added parameters**: per control matrix solve the protected ridge

```
ΔWᵀ = ( G_edit + λ_keep·G_keep + λ₂·I )⁻¹ · (X_editᵀ · dY / N_e)
```

where `X_edit` = pass-4 inputs, **`dY = Y³ − Y⁴`** (pass-3 outputs MINUS pass-4 outputs — the loop's own healthy pass as the supervision target), `G_keep` = pass-1..3 input Grams (soft null-space keeping default 3-pass behavior), `λ₂` = trace-normalized scale-invariant ridge, applied with a per-matrix Frobenius cap (`max_rel` 0.25). 168 BF16/FP32 **control** tensors edited (48 memory-gate projections + attention `o_proj` + MoE routers over L6–17); all 24.4B quantized experts bit-identical (integrity audit: 168/1244 keys changed, 0 expert, 0 vision). Result (self-reported): pass-to-pass cosine stabilizes through unseen pass 6 (0.949→0.972→0.989), 4-pass repeats 95.3%→0%, 4-pass DeepScaleR 3.1%→42.2% — **but still below 3-pass 50.0%**: the repair buys *stability*, not *utility* (see F1). Step 2 (GSPO SelfWrite, 4 self-verified generations over 326 control tensors, arXiv:2507.18071 recipe + loop-advantage bonus) is the training half — routing note.

**Distilled for katgpt-rs (modelless, inference-time):** FP-Solve is **modelless-lane legal by construction** (`torch.set_grad_enabled(False)`; a deterministically constructed weight correction — the raw/lora hot-swap class, §3.5 path 2). The genuinely NEW thing is not the solve (MEMIT-family protected ridge — shipped as `katgpt_core::closed_form_weight_write`) but the **supervision source**: an iterated computation's own deepest-healthy pass output as a free, label-free contraction target, with the keep set drawn from the same matrix's EARLIER PASSES (a pass-domain Gram keep) instead of authored prompt keys. Novelty is pinned NARROW (round-1 verdict correction): using the loop's own pass output as a target is KNOWN at TRAINING time (DEQ fixed-point/Jacobian regularization; pass-consistency losses in looped-LM training) — the new claim is the CLOSED-FORM inference-side solve with the pass-domain keep set on FROZEN weights, licensing depth extrapolation. This is the missing weight-space counterpart to our shipped runtime damping (Bench 699 `lt2_deep_stability`, `h ← (1−α)h + αF(h)`): damping treats depth-collapse per request in state space; FP-Solve repairs the dynamics once in weight space so deeper `loop_max` runs natively (MERGED-overlay posture — an unmerged rank-r overlay costs O(r·d) per token at serving; the cost census is a filed task). Filed: `.issues/1248`.

## 1. Paper Core Findings (numbers from the repo's own JSON artifacts, not the prose)

- **The fault (l17_fault.json):** pass-cosine healthy on L6–16 (≥0.68), collapses ONLY at L17 pass-2→3 (`cos = 0.172`); top-1 shift direction `v1` carries `top1_energy_pass3_shift = 0.7554`; per-pass projection `[-137.2, −121.2, +114.6, −81.1, −97.6]` — the loop's natural basin is negative-v1; pass 3 (last trained) spikes positive; pass 4 consumes messages from a gate-never-seen state. MLP memory-gate mean by pass `[0.566, 0.638, 0.067, 0.492]` — gate collapse exactly at the OOD-consuming pass.
- **The repair (fpsolve_results.json):** solve 353 s on 1 GPU; 168 matrices; `pass_cos_r6 = [0.9347, 0.2306, 0.9488, 0.9718, 0.9886]` — note the **2→3 transition stays broken (0.2306)**; the repaired ones are 3→4, 4→5, 5→6. `mean_rel_change = 0.246, max = 0.250` — **the cap saturates on nearly every matrix** (the unconstrained solve wants ~4× more movement; "closed-form direction, norm-bounded step").
- **Blind rows (integrity audit + paper Table 1):** 4-pass DeepScaleR 3.1%→42.2% (0% repeats); 3-pass GSM8K 93.8→96.9 (+3.1); LiveCodeBench 34.4→37.5; Olympiad 20.3→21.9; WinoGrande 68.7→70.0; ARC/HellaSwag 0.0 drift; **MMLU 82.5→81.4 (−1.1pp)** — a regression the prose omits.
- **GSPO half (gspo_results.json):** 327 keys changed (mean rel 0.008); hidden 3-mode gate 57.8%→62.5% over 4 generations; final ladder's best mode is the **2-step damped RK (64.1% > 4-pass 62.5% > 3-pass 60.9%)** — a zero-weight runtime mode out-scoring both depth settings (post-pipeline caveat: measured after FP-Solve+GSPO, not alone).

## 4. The honest boundary — falsifier catalog (extracted from the source's OWN artifacts)

1. **F1 — pseudo-fixed-point fallacy:** contracting pass-4 onto pass-3 assumes deeper passes carry no useful refinement. Their own data: post-FP-Solve 4-pass DeepScaleR = 42.2% **< 3-pass 50.0%** — the repaired extra pass is net-negative on math; only the GSPO generations flip it. Modelless expectation: "extended depth stops HARMING", never "depth pays".
2. **F2 — keep-drift is mixed-valence:** λ_keep is soft; 3-pass behavior drifts off the captured span. Measured: four 3-pass rows IMPROVE (lucky/beneficial drift — the contraction target never runs at 3-pass), MMLU −1.1pp. Never claim 3-pass preservation as identity; pre-register per-suite floors and accept mixed signs.
3. **F3 — the fault is contained, not fixed:** post-edit `pass_cos_r6[1] = 0.2306` — the pass-2→3 transition stays collapsed; pass-4 now PARKS in the +v1 spike basin instead of the loop's natural −v1 basin (benign-parking is untested beyond 6 passes and off math prompts). Gates must pin ALL transitions.
4. **F4 — covariance-span gap:** keep Grams from 48 near-identical template prompts ("solve equation kx+…") — rank-limited, domain-narrow; off-span inputs get the λ₂-minimal-norm edit: bounded, not zero. Fleet capture rides the serving corpus.
5. **F5 — cap saturation:** mean_rel 0.246 ≈ cap 0.25 on nearly every matrix — the trust region does real stabilization work; the claim is "bounded closed-form edit"; sweep the cliff.
6. **F6 — solve-path/serve-path skew:** captures+solve on the bf16 TF32 HF forward vs our dequant-overlay serving posture — capture on the SERVING forward, solve f32 pinned (Issue-940 fold-order), envelope digest bound to the serving build (the deletion-mask lane's discipline).
7. **F7 — precision/determinism:** TF32 + bf16 captures arch-deterministic but not arch-portable; `[::2]` stride subsampling and UNMASKED pad rows (left-padded batches feed pad activations into the Grams) are capture-policy hazards — fleet version masks pad rows and pins the stride.
8. **F8 — oscillation ≠ divergence:** a productive limit cycle (‖dY‖ flat/alternating, answers improving across passes) must NOT be contracted — detect first (depth telemetry), then choose the gentlest intervention (governor/damping modulate; the solve annihilates).
9. **F9 — conditioning edges:** near-duplicate prompts → near-singular G_edit; λ₂ floor keeps A SPD but null-span solutions go arbitrary — condition census + min-eigenvalue floor, fail loud.
10. **F10 — depth-specific overlays:** the solve is fit at forced depth 4 with targets from 3; deeper targets are their own overlays. Genuine positive: 4→5, 5→6 telemetry (0.972/0.989) was fit AT depth 4 — the repair generalized 1–2 steps past its fit depth, the strongest feasibility fact in the record. ⛔ Self-reported — Issue 1248 converts this narrative into a BAR: the `loop_depth_ood` fixture fits at d+1 and must hold at d+2/d+3 (bar (b)); ship depth-targeted envelopes; never claim one overlay fixes all depths.
