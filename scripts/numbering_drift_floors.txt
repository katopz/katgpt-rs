# Committed expectations for scripts/numbering_drift_sweep.py — the VOCABULARY
# half of the cross-repo numbering sweep (Issue 725). The population (which
# repos exist) is DERIVED from BOUNDARY.md + a .git dir and is never typed
# here; deriving both from one walk is what makes a cross-repo gate permanently
# green (the Issue 702 lesson, one instrument over).
#
# Format:  <repo>  <min_files>  <max_dup>  <max_above>  <max_malformed>  <max_resets>  <min_numbers>  <max_hist>
#
#   min_files      FLOOR over the ALLOCATOR-SERIAL dirs only
#                  (.plans/.issues/.research/.proposals). Every other column is
#                  a ceiling, and a ceiling cannot fail once the instrument
#                  goes blind — one regex regression takes the population to
#                  zero and all three pass, indistinguishable from a clean
#                  workspace. Pinned at ~80% of measured because files are
#                  legitimately REMOVED here per the noise-reduction rule; a
#                  floor at the measured value would red on every correct
#                  removal.
#   max_dup        tracked duplicate numbers. A RATCHET, not a wall — see below.
#   max_above      .highwater below its dir max: `value + 1` is already taken,
#                  so the next allocation is GUARANTEED to collide.
#   max_malformed  .highwater present but not a bare integer.
#   max_resets     commits (or merge resolutions) whose counter value landed
#                  below max(parent values) — Issue 770's per-commit-parent
#                  walk. After `517→511` the re-climb re-spends numbers: the
#                  never-reuse rule broken at counter granularity. A RATCHET
#                  at the measured count — a NEW reset reds, the standing
#                  history stays visible here. The unit is reset ROWS (one
#                  commit each), NOT distinct incidents: `627→614 ×2` is two
#                  commits, and one incident can surface as more than one
#                  row (e.g. the lower-side resolution on a branch and again
#                  at the merge that carries it). Lower a pin by the rows the
#                  repair removes, never by the incidents you counted.
#   min_numbers    FLOOR on the HISTORY walk (Issue 820) — distinct numbers
#                  recovered by `git log -M --diff-filter=D` PLUS what is on
#                  disk. It is NOT a second min_files and the two break
#                  SEPARATELY, which is the whole reason both exist: min_files
#                  counts tracked documents in the worktree, so a git-log
#                  regression leaves it untouched while collapsing this one to
#                  the on-disk count — and max_hist below then passes green
#                  over a blind instrument. Pinned at ~85% of measured, the
#                  min_files reasoning (numbers leave the walk only by a
#                  history rewrite, so the slack is smaller).
#   max_hist       numbers held by 2+ documents across HISTORY. A RATCHET at
#                  the measured count, for max_dup's reasons below and one
#                  more: 113 of the 183 are in repos this session does not own.
#                  ⛔ This column is NOT a stricter max_dup — it is the class
#                  max_dup CANNOT SEE. A document closed under the
#                  noise-reduction rule is DELETED, so a collision where both
#                  holders have closed leaves nothing in the worktree and
#                  max_dup reads 0. Measured 2026-09-17: max_dup totalled 0
#                  workspace-wide against 183 here. Never pool them.
#
# ── the UNMEASURED rows, and why their ceiling is 0 rather than something safe
#
# Seven repos are absent from this box (partial clone) and their two new
# columns could not be measured. They carry `0 0` and say so on the row. The
# min_numbers 0 is a floor that cannot fire and is disclosed as such; the
# max_hist 0 will RED for any of them that has collisions, on the first
# canonical-workstation run. That is deliberate and it is the lesser evil: a
# ceiling invented to be comfortable is a ceiling that never fires, which is
# this file's own stated failure mode one column up. Re-pin all seven from one
# full-checkout run — the wasm32_surface_drift_floors TOTALS precedent.
#
# ── why max_dup is a ratchet at the measured value, not 0 ───────────────────
#
# 35 tracked duplicates existed across four repos at the first sweep
# (2026-09-05); ALL now resolved — riir-ai's 6 the same day (T4b), riir-clippy's
# 4 via its Issue 069 (58e7c1d, owner go), riir-train's 13 via its Issue 514
# (103ed351, hand reads overturned the UNDECIDABLE verdicts) — so the standing
# backlog is 12 in mmorpg-editor, which is READ-ONLY to these sessions
# (report only). Resolving one is a citation-weight arbitration, not a rename:
# Issue 724 T2's precedent is that the file with the most inbound mentions
# KEEPS the number and the other moves to a fresh one, which requires reading
# the corpus and updating every citation. Three of the four repos are owned by
# other sessions and mmorpg-editor is read-only to this one. A pin of 0
# would red on landing and be ignored by the next reader — the failure mode
# docs_gate.sh's preamble records. Pinned at measured, so a NEW collision reds
# immediately while the standing backlog stays visible in this file instead of
# silently tolerated.
#
# LOWER a repo's pin in the commit that resolves one of its collisions. Never
# raise one without the reason in the commit message.
#
# ── the zeros are load-bearing ──────────────────────────────────────────────
#
# max_above and max_malformed are 0 EVERYWHERE because all seven were repaired
# in the sweep's landing commit (5 malformed + 2 stale). Those are one-line,
# value-preserving repairs with no arbitration attached, so there is no reason
# to tolerate a single one. A regression reds.
#
# ── max_resets: the 770 correction, and why the 769 numbers were wrong ─────
#
# The Issue-769 landing pinned resets from a walker that ordered ALL refs'
# hunks by commit DATE around one `current`: 15 of its 31 rows named
# FORWARD-stepping commits (phantoms from lineage interleaving — riir-chain's
# entire ×4 and riir-train Issue's ×2 were phantoms), and it could not see
# MERGE commits at all (`git log -p` emits no merge diffs), so its "all 31 are
# non-merge stale-lineage writebacks" adjudication was true BY CONSTRUCTION.
# The Issue-770 walk (verdict-review findings 1+2) judges every HEAD-reachable
# commit against its OWN parents' blob values: merge resolutions taking the
# lower side are now visible and correctly blamed (riir-ai Issue 627→614 at a
# Merge commit; mmorpg-editor Plan 152→150 ×3 at merges). Corrected count:
# 27 workspace-wide. Same doctrine as max_dup — the standing history is
# COMMITTED (un-committing it rewrites every repo's past; the hazard was
# absorbed by gap fast-forwards and push-wins renumbers; the max_dup column
# proves no live file duplicates). A pin of 0 would red on landing for seven
# repos and be ignored. The ratchet catches the NEXT one.
#
# The walk is HEAD-reachable only, never --all: pins are a function of the
# branch the box carries, not of which refs happen to be fetched.
#
# ⛔ There is deliberately NO max_unbumped column (Issue 770 finding 4): the
# worktree-below-history-max quantity is checkout state — mmorpg-editor's
# bevy worktree reads 191 while other refs sit at 194 — a pin would be ref-set
# dependent and red on a box that owes nothing. It is PRINTED by the sweep
# every run, never gated.
#
# ── the `216defb9b` walker defect: WHICH rows here read corrupt values ───
#
# That commit fixed the walker (the reader framed `cat-file --batch` by LINE,
# so one two-line `.highwater` blob shifted every older commit's value) and
# recorded the effect on COUNTS: workspace resets 46 → 28, riir-ai 26 → 9,
# riir-clippy 5 → 4. That is the wrong quantity for adjudicating THIS file.
# A pin is sound only if the values behind it were read correctly, and a
# history can be corrupt WITHOUT its reset count moving — so the question
# every row here needs answered is not "did my number change" but "was my
# repo's counter history being read wrong at all".
#

# riir-train 2, riir-mmorpg-examples 1 — sat on a history read CORRECTLY
